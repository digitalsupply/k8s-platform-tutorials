## 三、必须更正的结论

### 更正 1：apiserver 192 次重启 ≠ 集群不稳定

我在上一轮说：

> "apiserver 自己重启了近 200 次…它是集群里最不稳定的组件"

**这个判断是错的。** 192 次重启**全部发生在 PVE 断电期间**（数月内多次开机关机，每次容器被强杀，重启计数累加）。**本次开机后 4 天多内，apiserver 一次都没重启过。**

同理，「11 个组件在 01:50 同时 Error」的根因也需重新审视——那**不是** apiserver 不稳（那时 apiserver 运行正常），而是需要单独排查。已确认的事实：
```
ceph-csi csi-provisioner 日志：
  E0930 01:51:27  failed to renew lease: context deadline exceeded
  E0930 01:51:27  "Stopped leading"          ← 主动让位，不是崩溃
  I0930 01:51:49  successfully acquired lease  ← 20 秒后恢复
```
这是 leader election 因 apiserver 响应慢而优雅重启，属**自愈行为**。当时同秒发生的还有 cnpg-controller、kube-vip、VPA、nfs-provisioner——**全是依赖 apiserver 做协调的组件**，说明是 apiserver 的一次瞬时延迟（约 20 秒）触发了集体重选。

### 更正 2：告警规则确实在误报（但方向反了）

我上一轮说 `KubePodHighRestartCount` / `KubePodCriticalComponentHighRestart` "在正常工作"。**在当前语境下它们是误报**——因为：

- 所有"高重启"计数都是**断电期间的历史累加值**
- 计数器是**单调递增**的，不会因时间推移而衰减
- 规则写的是"累计 > 10 次"，所以**永远会 firing**，直到 Pod 被重建

**这是规则设计缺陷**：用累计计数做告警，在"长期停机后开机"场景下必然全部触发。正确做法应该用 `increase(...[1h])`（窗口内的增量）而非 `status_restarts_total`（历史累计）。

### 更正 3：告警噪音的真正来源

此前我给建议说"关掉这两条告警"或"改成近 1 小时新增重启"——现在明确了：
- 现有规则**每次开机后必然全部 firing**，且永不恢复
- 应改为窗口增量，且需要 Pod 重建或计数清零才会消失

### 更正 4：容量与性能的判断需要加限定

此前所有报告隐含假设"这是独立的生产集群"。实际是**单物理机 + 9 VM + 60 节点当量**的实验环境。评估故障影响时必须考虑：

| 层面 | 风险 |
|---|---|
| **单点** | PVE 宿主机宕机 = K8s 全挂 + Ceph 全挂 = **存储与调度同时消失** |
| **无冗余** | 无第二台 PVE，无冷备，VM 无 HA（无 DRBD/共享存储） |
| **重启代价** | 断电数月的场景说明这是**实验环境**，不具备生产 SLA |
| **数据安全** | Ceph 副本数 3 但 3 副本都在同一物理机 —— **抗不了物理故障** |

**Ceph 副本 3 份却全在一台机器上**，是典型的"伪冗余"：能抗 OSD/VM 故障，抗不了宿主宕机或磁盘损坏。

## 五、由此暴露的真实问题

### 🔴 P0：单点架构

```
        ┌──────────────┐
        │  PVE 宿主机   │  ← 10.0.0.1，单机
        │  (42 vCPU/64G)│
        └──────┬───────┘
     ┌─────────┴─────────┐
     │                   │
┌────▼─────┐        ┌────▼─────┐
│ 6 K8s VM │        │ 3 Ceph VM│
│ 28C/43G  │        │ 14C/18.5G│
└──────────┘        └──────────┘
   K8s 集群            Ceph 集群
   （挂了就全挂）      （挂了PV就没了）
```

**任何宿主机级故障（硬件、磁盘、意外断电）会同时摧毁两个集群。** 这是当前架构最大的风险，没有告警能覆盖。

### 🟠 P1：Ceph 副本无物理冗余

6 个 OSD、3 副本、3 个 mon 全在**同一台物理机**的虚拟磁盘上：
```
ceph-01: sda 80G (OS) + sdb 30G
ceph-02: sda 80G (OS) + sdb 30G
```
- 宿主机磁盘损坏 → **所有 OSD 同时丢失** → 数据全毁（3 副本也救不了）
- 虚拟磁盘是文件，底层若是单块物理盘，等于把 3 副本写在同一块盘上

### 🟠 P1：Ceph OSD 容量偏小

`ceph df` 显示 180 GiB 总量、已用 18 GiB（10%），`MAX AVAIL` 各 pool 50 GiB。而 K8s 的 Loki 日志会持续写入这个池——若日志量增长，**Ceph 会先于 K8s 磁盘成为瓶颈**。

### 🟡 P2：我的告警规则需要按实验环境重新设计

在"长期停机 + 频繁开关机"的场景下：
- 累计计数类告警（`status_restarts_total`）**永远误报**
- 应该改用**窗口增量**（`increase(...[1h])`）或直接监控 CrashLoopBackOff 状态
- 建议增加"宿主机重启检测"告警（node boot time 变化），这才是真正的开机事件信号
