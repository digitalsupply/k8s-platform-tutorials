> 审计对象：生产集群（6 节点 kubeadm 集群）

## 摘要

**结论：1.35 升级本身的 7 项 P0 硬性要求，你已经全部满足，且做得干净。** 底层（cgroup v2 / containerd 2.x / runc 1.4.3）完全达标，没有历史包袱。

但审计发现了 **3 个真实存在的问题**（与 1.35 升级无关，是既有隐患）和 **2 个 1.35 特性未被利用的机会**。

工具链方面：**VPA 1.6.0、MetalLB 0.13.12、ceph-csi 3.16.2 三个组件版本明显落后**，是本轮最需要处理的。

## 第二部分：审计发现的真实问题

### 🔴 问题 1：`kube-vip` 挂载 `admin.conf`，且已崩溃 51–53 次

**这是本次审计发现的最严重问题，与 1.35 无关但必须处理。**

```yaml
# kube-system/DaemonSet/kube-vip-ds
volumes:
- name: kubeconfig
  hostPath: { path: /etc/kubernetes/admin.conf }   # ⚠️ cluster-admin 凭据
containers:
- securityContext:
    capabilities: { add: [NET_ADMIN, NET_RAW] }    # ⚠️ 提权能力
```

**两个独立问题：**

**(a) 凭据暴露**
`/etc/kubernetes/admin.conf`（含 `kubernetes-admin` 的 **cluster-admin** 客户端证书与私钥）被 hostPath 挂进容器，而该容器具备 `NET_ADMIN` + `NET_RAW`。这是官方文档明确不建议的用法：容器一旦被攻破，攻击者直接拿到集群最高权限 + 宿主网络栈控制权。

日志里的错误正好印证了这条路径：
```
User "kubernetes-admin" cannot get resource "leases" in API group "coordination.k8s.io"
```
kube-vip 确实在用 admin.conf 里的 cluster-admin 身份。

**(b) 反复 panic 崩溃**
```
3 个 Pod，restartCount = 51 / 53 / 53（259 天）
panic: [recovered, repanicked]
  github.com/kube-vip/kube-vip/pkg/cluster.(*Cluster).StartCluster.func4()
    /src/pkg/cluster/clusterLeaderElection.go:246
```
崩溃日志显示根因是 leader election 期间 **apiserver 不可达**（`dial tcp 127.0.0.1:6443: connect: connection refused`）——正好对应你这次升级重启 apiserver 的时刻。kube-vip v1.0.3 在 apiserver 短暂不可用时会**直接 panic 退出而非重试**（exitCode 2）。

**影响**：VIP `10.0.0.168` 由 kube-vip 提供（`cp_enable=true`，ARP 模式）。反复崩溃意味着**控制面 VIP 的 HA 保障并不可靠**。

**修复建议**：
1. 改用**最小权限 ServiceAccount** + 专用 RBAC（仅需 `leases` 的 get/create/update，以及 `nodes` 的 patch，用于 `enable_node_labeling`），彻底移除 admin.conf 挂载
2. 升级 kube-vip（当前 v1.0.3，见下节）
3. 为该 DaemonSet 加 `priorityClassName: system-cluster-critical`

### 🟡 问题 2：kube-proxy 仍是 `iptables` 模式

1.35 已弃用 `ipvs`，官方推荐方向是 **`nftables`**。你目前在 `iptables`——不算错误，但错过了一次性能与可维护性优化：

- **性能**：`iptables` 模式下 kube-proxy 规则是**线性遍历**，Service/Endpoint 数量大时 CPU 开销随规模线性增长；`nftables` 用 nftables set（哈希表），查找是 O(1)
- **可维护性**：iptables 规则链数量随 Service 数膨胀，重启时规则回放慢；nftables 是事务化的，一次性原子替换
- **未来**：1.35 弃用了 ipvs，说明上游在收敛到 nftables。现在迁移，等于提前站好位置

考虑到你集群规模不大（3 worker、约 70 个 Deployment），**当前 iptables 模式完全够用**。建议列入技术债，不必现在动。

`ceph-rbd-sc` 的 reclaimPolicy 是 `Retain`，所以 PVC 删除后底层 RBD 镜像**永久残留**，持续占用 Ceph 存储池空间且不会自动回收。

### 🟢 问题 4：`kubelet` / `kubeadm` 版本细节

1.35 的几个细节确认：

| 项 | 当前值 | 说明 |
|---|---|---|
| `imageMaximumGCAge` | `0s`（未启用） | 1.35 已 **GA** 的「按最大镜像年龄回收镜像」（KEP-4210）。设为 `0s` 意味着**永不按年龄清理**，节点磁盘只靠 85% 水位线触发。建议设为 `168h`（7 天） |
| `seccompDefault` | `false` | 1.35 的 `SeccompDefault` 特性。设为 `true` 可让**所有 Pod 默认使用 RuntimeDefault seccomp**，是低成本高收益的安全加固。需先验证 Calico/Ceph-CSI/MetalLB 兼容性 |
| `imagePullCredentialsVerificationPolicy` | `NeverVerifyPreloadedImages`（默认） | 1.35 的 KEP-2535 已默认开启，但策略取的是**最宽松档**：非 kubelet 拉取的预置镜像免校验。若为多租户且跨团队使用私有镜像，建议评估切到 `AlwaysVerify` |
| PodSecurity 标签 | **仅 metallb-system 有** | 其余 20+ 命名空间**完全没有** Pod Security Admission 约束。可考虑给业务命名空间至少加 `audit=restricted` / `warn=restricted` 逐步推进 |

### ⚠️ 特别说明：节点拓扑标签为什么没生效

1.35 的 `PodTopologyLabels` 准入控制器**已默认启用**，但你的 Pod 上**没有任何拓扑标签**。核查原因：

```
# 节点上的标签（自定义命名，不符合标准）
worker01   zone=test-a
worker02   zone=test-b
worker03   zone=test-a

# 标准拓扑标签（缺失）
（无）topology.kubernetes.io/zone
（无）topology.kubernetes.io/region
```

准入控制器只同步**标准的 `topology.kubernetes.io/zone` 与 `topology.kubernetes.io/region`** 标签。你用的是自定义的 `zone`，控制器识别不到，所以没有可复制的源标签。

**修复方法**（二选一或都做）：

```bash
# 方案 A：补标准标签（推荐，一次性）
kubectl label node worker01 topology.kubernetes.io/zone=test-a --overwrite
kubectl label node worker01 topology.kubernetes.io/region=test-a --overwrite
kubectl label node worker02 topology.kubernetes.io/zone=test-b --overwrite
kubectl label node worker02 topology.kubernetes.io/region=test-b --overwrite
kubectl label node worker03 topology.kubernetes.io/zone=test-a --overwrite
kubectl label node worker03 topology.kubernetes.io/region=test-a --overwrite
```

> 补完标签后，**新建的 Pod** 才会带上这些标签，且下游组件即可用 Downward API 读取（`spec.nodeSelector` / `topologySpreadConstraints` 也能直接用标准键）。
>
> 注意：这也意味着你的 `zone=test-a/test-b` 拓扑（worker01+worker03 为 a，worker02 为 b）**并非均衡分布**（2:1），如果有拓扑感知调度需求可以重新规划。
