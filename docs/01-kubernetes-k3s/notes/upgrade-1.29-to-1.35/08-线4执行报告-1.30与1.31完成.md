## 三、⚠️ 1.31 升级中的 apiserver 宕机事件（必须记录）

### 3.1 现象

集群从「节点显示 1.30.14、服务端已是 1.31.14」的不一致状态，逐步演变为**3 个 apiserver 全部无法启动**，整个集群不可访问。

### 3.2 完整因果链

```
① worker 阶段 kubelet 装包成功，但 apt-mark hold 阻止了服务重启
   → 磁盘包1.31.14，运行中的进程仍是 1.30.14
   → 手动 systemctl restart kubelet（6 节点）
       ↓
② m01 重启 kubelet 后，所有 Pod sandbox 创建失败：
   open /run/systemd/resolve/resolv.conf: no such file or directory
       ↓
③ m01 是 Rocky Linux 9.6，/run/systemd/resolve/ 不存在
   （systemd-resolved inactive，DNS 由 NetworkManager 管理）
       ↓
④ apiserver 是静态 Pod，也需要 sandbox → 起不来
   → m01 apiserver 挂 → 所有节点（controlPlaneEndpoint 指向 m01）全部失联
   → 5 节点 NotReady
       ↓
⑤ 手动创建 /run/systemd/resolve/resolv.conf 后 sandbox 恢复
   但仍报 StartContainer 失败：
   "container not found"（containerd 元数据里旧容器记录未清理）
       ↓
⑥ crictl rm -a 清理 + 重启 kubelet → 3 个 apiserver 全部恢复
```

### 3.3 三个可复用的教训

**① `apt-mark hold` 会阻止 kubelet 重启**

我在脚本里加 hold 是为了「防止意外自动变更」，但**副作用是装完包不会自动重启服务**。

**修正**：脚本中 `install_pkgs` 之后必须显式 `systemctl restart kubelet` 并**验证进程启动时间晚于安装时间**。

**② Rocky vs Ubuntu 的 resolv.conf 路径差异**

- Ubuntu 22.04：`/run/systemd/resolve/resolv.conf` 存在
- Rocky 9.6：**不存在**（systemd-resolved 未启用）

kubelet 未指定 `--resolv-conf` 时默认用该路径。**在 Rocky 节点上重启 kubelet 会导致全节点容器起不来。**

**修正**：升级前检查该文件存在，不存在则创建（或给 kubelet 显式指定 `--resolv-conf=/etc/resolv.conf`）。

**③ containerd 里的孤儿容器记录**

kubelet 重启后，旧容器已删除但 containerd 元数据未清理，导致 `StartContainer` 报 `container not found` 且持续失败。

**修正**：升级流程中加 `crictl rm -a`（清理已退出容器）+ 重启 kubelet。
