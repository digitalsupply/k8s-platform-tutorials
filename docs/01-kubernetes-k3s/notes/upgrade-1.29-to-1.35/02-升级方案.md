## 二、补充排查结果（本阶段新查清）

### 2.1 ★ 重大发现：kube-proxy 使用 IPVS 模式

```yaml
# cm/kube-proxy
mode: "ipvs"
masqueradeAll: false
```

实测 worker01 上**IPVS 规则真实在跑**：
```
ipvsadm -Ln | wc -l  →  366        ← 366 条虚拟服务规则
lsmod | grep -c ip_vs → 5          ← 内核模块已加载
```

**风险等级：高。** 见 §3.3 的 IPVS 弃用分析。

### 2.2 集群 API 版本与 CRD 盘点（142 个 CRD）

集群用的是**大量云原生组件**，逐个确认是否使用已在 1.30-1.35 移除的 API：

| 组件 | CRD 数量级 | 已移除 API 风险 |
|---|---|---|
| Traefik (hub.traefik.io) | ~25 个 | 低（Traefik 3.6.2 新版，跟进及时）|
| Calico (crd.projectcalico.org) | ~20 个 | 低（v3.27.4 用 v1 API）|
| Knative (serving/eventing/sources/messaging) | ~35 个 | 低（API 稳定）|
| Prometheus Operator | ~15 个 | 低 |
| Tekton Pipelines/Triggers | ~20 个 | ⚠️ 需在升级各小版本时复查 |
| Strimzi / Kafka | ~10 个 | ⚠️ 同上 |
| cert-manager | 5 个 | 低 |
| CNPG (postgresql) | ~8 个 | 低 |
| MetalLB | ~15 个 | 低 |
| ArgoCD | 3 个 | 低 |

**已确认的安全项**：
- 无 `PodSecurityPolicy`（PSP 在 1.25 就已移除，本集群本就没有）
- 无 `flowcontrol.apiserver.k8s.io/v1beta3`（1.32 移除，本集群无 FlowSchema/PriorityLevelConfiguration）
- 所有内置资源已用 v1 版本

**★ 需人工确认**：Tekton 与 Strimzi 各小版本的 CRD API 兼容矩阵，需在升级到对应小版本前用官方 pluto 工具实扫（见 §6）。

### 2.3 ★ CNI 差异已查清：无影响，不必处理

**差异实况**：

| 节点类型 | /opt/cni/bin 插件 | 数量 |
|---|---|---|
| m01 / master01 / master02（control-plane）| calico, calico-ipam, portmap, bandwidth, loopback, host-local, flannel, tuning | **8** |
| worker01/02/03 | 上述 8 个 + bridge, dhcp, dummy, firewall, host-device, install, ipvlan, macvlan, ptp, sbr, static, tap, vlan, vrf | **24** |

**为什么无影响**（实测两节点 `/etc/cni/net.d/10-calico.conflist`）：

```json
{
  "name": "k8s-pod-network",
  "cniVersion": "0.3.1",
  "plugins": [
    { "type": "calico", "ipam": {"type": "calico-ipam"}, "policy": {"type": "k8s"} },
    { "type": "portmap", "snat": true },
    { "type": "bandwidth" }
  ]
}
```

**两边的 conflist 完全相同，实际只用到 3 个插件**：`calico` / `calico-ipam` / `portmap` / `bandwidth`。

- control-plane 的 8 个插件**已完全覆盖**实际使用的插件 → 不会缺
- worker 上多出的 16 个（bridge/install/dhcp/macvlan 等）是**历史遗留**（可能来自 flannel 或更早期的 CNI 安装），未被任何 conflist 引用

**结论**：
- **不影响 containerd 升级**，无需统一
- 建议**保持现状**（不要为了"看起来一致"去删 worker 上的插件——虽然它们无用，但删除有风险且无收益）
- 若雷浩想清理，可另开任务：worker 上 16 个无引用插件删除（**低优先级，非升级前置条件**）

### 2.4 ★ registry.auths / configs 已查：均为空，无需处理

实测 `/etc/containerd/config.toml`：
```toml
[plugins."io.containerd.grpc.v1.cri".registry]
  [plugins."io.containerd.grpc.v1.cri".registry.auths]      ← 存在但无条目
  [plugins."io.containerd.grpc.v1.cri".registry.configs]    ← 存在但无条目
  [plugins."io.containerd.grpc.v1.cri".registry.mirrors]   ← 存在但无条目
  [plugins."io.containerd.grpc.v1.cri".registry.headers]   ← 存在但无条目
```

**四个 registry 子段全部为空** → 官方文档中「升2.x 需改用 `config_path`」的迁移要求**对本集群不适用**。

**当前镜像拉取策略**：只靠 `sandbox_image` 指向 aliyuncs，其余镜像走默认（Docker Hub / quay.io / registry.k8s.io）。实测集群内确实有拉自 quay.io（cephcsi）、docker.io（calico）、ghcr.io（knative）、registry.k8s.io（csi-*）的镜像。

### 2.5 磁盘清理方案（决策 6：可以清理）

雷浩判断"不需要备份容器，磁盘空间够"。核实：

| 节点 | containerd 数据 | 可用 | 升级实际需要额外磁盘 |
|---|---|---|---|
| worker01 | 26G | 9.9G | **仅约 100-200MB**（新二进制 + pause 镜像）|
| worker02 | 27G | 9.1G | 同上 |

**确认：升级不需要备份容器数据**。理由：
1. containerd **原地替换二进制**，不动 `/var/lib/containerd` 里的镜像和容器
2. 新 containerd 首次启动会拉取新 pause 镜像（仅几十 MB）
3. 容器不会重建（重启 containerd 服务不影响运行中的容器）

**但清理仍有价值**（可选，非必需）：
```bash
# 查看可回收空间
crictl rmi --prune    # 清理未使用的镜像
crictl rmp -a         # ⚠️ 只清理已退出容器，需确认无有用调试容器
```
**建议**：可以清理 `crictl rmi --prune`，但**不必为升级特意做**——9-10G 余量对 200MB 的需求绰绰有余。

## 三、★ 兼容性核查结论（决策 7）

### 3.1 Calico v3.27.4

| 项 | 结论 |
|---|---|
| 当前版本 | `docker.io/calico/node:v3.27.4` |
| 官方文档（最新 3.32）测试范围 | K8s **1.34 / 1.35 / 1.36** |
| 对 containerd 2.x 的要求 | Calico 通过 CRI 与 containerd 交互，**官方未列 containerd 版本限制**（只要求 K8s 版本） |
| cgroup 要求 | 需 CAP_SYS_ADMIN；用 systemd cgroup（已满足）|
| 内核要求 | 5.10+（m01 是 5.14、其余 5.15，**满足**）|
| CNI 插件 | 用 `calico` 类型，不依赖 containerd 内置 CNI |

**结论：Calico v3.27.4 与 containerd 2.x 无已知冲突**。它通过标准 CRI API 工作，containerd 1.x→2.x 的 CRI v1 接口不变。

⚠️ **但需注意**：Calico v3.27.4 官方测试的 K8s 版本范围是 **1.24-1.27 时代**（v3.27 发布于 2024）。而**最新 Calico v3.32 才明确测试 1.34/1.35/1.36**。

**这意味着一个独立于 containerd 的问题**：**Calico v3.27.4 是否支持 K8s 1.35，需要单独确认**。
- 好消息：Tigera 文档说 "Other versions may work, but we are not actively testing them"
- **建议**：在升级 K8s 到 1.34/1.35 之前，查 Calico 官方 release notes 确认；或考虑把 Calico 也升级到 v3.32（**这会成为独立的一条升级线，需人工决策**）

### 3.2 Ceph-CSI v3.16.2

| 项 | 结论 |
|---|---|
| 当前版本 | `quay.io/cephcsi/cephcsi:v3.16.2` |
| 依赖的 k8s.io 库 | release note 显示 v3.16 已 bump到 `k8s.io/api 0.35.0`、`k8s.io/kubernetes 1.34.2` |
| 对 containerd 2.x | **通过 CSI gRPC 与 containerd 无关**，只用标准 CSI 接口 |
| 对 K8s 1.35 | ✅ **v3.16.2 内部依赖已 bump 到 k8s.io 1.34/0.35，兼容性良好** |

**结论：Ceph-CSI v3.16.2 是目前组件中与新 K8s 版本兼容性最好的**（2026 年发布，依赖已跟上）。无 containerd 2.x 兼容问题。

⚠️ **一个已知警告（官方 release note）**：
> Ceph Tentacle v20.2.0 may have data loss with CephFS when readAffinity is enabled

本集群用 `ceph-csi-rbd` 命名空间（**RBD**，不是 CephFS），且需确认 Ceph 版本是否 Tentacle v20.2.0（**需人工确认**）。若用 RBD 则此警告不适用。

### 3.3 ★★ 最高风险：kube-proxy IPVS 在 K8s 1.35 被弃用

**这是本次核查最重要的发现**，独立于 containerd。

**官方声明**（KEP-5495）：
- **K8s 1.35 弃用 IPVS 模式**
- **1.38 移除 IPVS**
- 官方建议迁移路径：1.35 先在测试环境验证 nftables → 小集群可考虑直接用 iptables

**本集群实况**：
- `mode: "ipvs"`，worker01 上 **366 条活跃规则**，内核模块已加载

**风险评估**：
- **1.35 升上去还能用**（只是弃用告警，不会立即坏）
- **但 1.38 会移除**，届时必须迁移

**建议**：把「kube-proxy 从 ipvs 迁移到 nftables 或 iptables」**纳入本次升级计划**，或至少在升到 1.35 前评估：
- 小规模集群（本集群 6 节点）→ **iptables 足够**，迁移最简单
- 或迁移到 **nftables**（K8s 1.31+ GA，性能更好）

**★ 这是需要雷浩决策的第 9 个确认项**：是否在本次升级中一并迁移 kube-proxy。

## 四、目标版本定稿（决策 8：LTS）

### **containerd 2.3.x（LTS）**

| 依据 | 内容 |
|---|---|
| 官方状态 | **LTS**，EOL **2028-04-30**（最长支持期）|
| 官方升级路径 | 明确支持「**1.7(LTS) → 2.3(LTS)**」直接跨 major 升级 |
| config 版本 | v4（本集群 v2→v3/v4 均可）|
| K8s 1.35 矩阵 | 官方列 2.2.0+/2.1.5+/1.7.28+，**未直接列 2.3**（2.3 是 1.36 的推荐）|

**★ 诚实说明这个取舍**：2.3 是 LTS、支持到 2028，但 K8s 1.35 的官方推荐矩阵里没有它。理由分析：
- containerd 官方声明"任何 actively supported 版本都可能有补丁，矩阵只是「经过最充分测试」的推荐"
- 2.3 是 1.36 的推荐版本，**向上兼容 1.35**（CRI v1 接口一致）
- 支持期最长 vs矩阵推荐，是个真实取舍

**如果雷浩更倾向保守**，备选是 **2.2.x**（Active，1.35 官方推荐，但 2026-11 EOL）——但那时 1.35 刚升完 containerd 就又要考虑升级，**长期反而更折腾**。

**我的建议仍是 2.3.x LTS**：一次升到位，撑到 2028，比升到 2.2 半年后再升 2.3 更省事。

## 五、升级顺序与滚动策略

### 5.1 总体顺序

```
★ 阶段 A：升级 containerd + runc（K8s 仍为 1.29）
  A1. 选 1 台 worker 做试点（建议 worker03 — 业务负载最少）
  A2. 验证通过 → 滚动其余 5 台
  ★ 此时 K8s 版本不动，验证 containerd 兼容性

★ 阶段 B：逐级升级 K8s
  1.29 → 1.30 → 1.31 → 1.32 → 1.33 → 1.34 → 1.35
  ★ 每级：control-plane 先升，验证后再升 worker
  ★ 每级之间必须等Prometheus/Grafana/业务全部健康

★ 阶段 C（独立评估项）：kube-proxy IPVS → nftables/iptables 迁移
  ★ 是否纳入本次升级待雷浩决策
```

### 5.2 为什么先 worker 后 control-plane（阶段 A）

| 理由 | 说明 |
|---|---|
| 可回滚性 | worker 出问题不影响集群控制面，apiserver 仍能调度 |
| 验证充分性 | worker 上跑业务（监控、日志、CSI），能验证 containerd 兼容性 |
| 若成功再动 control-plane | 风险可控 |

**但 K8s 升级（阶段 B）顺序相反：control-plane 先升**——因为 kubeadm 要求 control-plane 先于 worker 完成升级（版本 skew 策略）。

### 5.3 单节点滚动流程（阶段 A：containerd）

```bash
# ── 1. 驱逐（在控制节点执行）
kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --force
   ↑ --ignore-daemonsets: 跳过 Calico/node-exporter/alloy 等 DaemonSet
   ↑ --force: 允许驱逐无控制器管理的 Pod（如 trf-doc 这类裸 Pod）

# ── 2. 节点侧备份与替换（在目标节点执行）
cp /usr/local/bin/containerd /usr/local/bin/containerd.bak-1.7.22
cp /usr/bin/runc /usr/bin/runc.bak-1.3.3          # m01
cp /usr/local/sbin/runc /usr/local/sbin/runc.bak-1.3.3   # 其余节点

# 下载 containerd 2.3.x + runc 1.4.x
tar -xf containerd-2.3.x-linux-amd64.tar.gz -C /
# ★ 注意：2.x 的 tar 包结构与 1.x 不同，containerd 二进制在 ./bin/
# ★ runc 需统一安装到 /usr/local/sbin/runc

# ── 3. config.toml 处理（★ 建议先不动）
# 建议：保留现有 version = 2，containerd 2.x 会自动按 v3 解析
# 若需启用 2.x 新特性再考虑 migrate
# 备份：cp /etc/containerd/config.toml{,.bak}

# ── 4. 重启与验证（在节点执行）
systemctl restart containerd
containerd --version        # 应显示 2.3.x
crictl info                 # 应无 error
crictl ps -a                # 容器数量应与升级前一致，无重建

# ── 5. 节点 Ready 验证（控制节点）
kubectl get node <node>              # 应为 Ready
kubectl get pods -A --field-selector spec.nodeName=<node>   # Pod 应正常

# ── 6. 恢复调度
kubectl uncordon <node>
```

### 5.4 control-plane 节点的 drain 注意（决策 3：看着办）

本集群 control-plane 是 **kubeadm 静态 Pod**（`kube-apiserver` / `etcd` / `controller-manager` / `scheduler`），在 `kube-system`。

| 要点 | 处理方式 |
|---|---|
| **etcd 是单副本还是多副本** | ⚠️ **需人工确认**。若 etcd 是单副本（实验环境很可能），**drain 该节点会导致集群完全不可用** |
| **静态 Pod 不受 drain 影响** | kubeadm 静态 Pod 无 owner controller，drain 不会驱逐它们 → 反而安全 |
| **必须避免** | 绝不能`delete` apiserver/etcd 的 Pod（MirrorPod），会导致停机 |
| **推荐做法** | control-plane 节点：**cordon → 确认无业务 Pod → 升级 → uncordon**，**不做 drain**（静态 Pod 本来就不需要驱逐） |
| **etcd 健康检查** | 升级前后都要确认 etcd 集群健康 |

**★ 明确建议**：control-plane 节点**只 cordon，不 drain**。理由：
1. 静态 Pod 不受 drain 管辖，drain 没有意义
2. 实验环境 etcd 若是单副本，drain 可能引发非预期后果
3. 业务 Pod 本来就不会调度到 control-plane（除非有容忍）

### 5.5 节点处理顺序

**阶段 A（containerd）**：
```
1. worker03  （试点，业务负载最少）
2. worker02
3. worker01
4. master01
5. master02
6. m01       （最后，Rocky 系统差异）
```
每台升级后**必须验证通过**再动下一台。**不并行**。

**阶段 B（K8s）**：control-plane 先升（kubeadm 要求）：
```
1. m01 → master01 → master02    （control-plane 逐个）
2. worker03 → worker02 → worker01
```

## 七、config.toml 迁移与回滚方案

### 7.1 ★ 建议：本次升级**不迁移** config.toml

**理由**（基于官方明确警告）：

> "Migrating a configuration to the latest version will limit the prior versions of containerd in which the configuration can be used. It is suggested not to migrate your configuration file until you are confident you do not need to quickly rollback your containerd version."

| 项 | 值 |
|---|---|
| 当前 config | `version = 2` |
| containerd 2.3 支持 | v2 / v3 / v4 均可读（官方确认 "All prior versions are supported by migration"）|
| **决策** | **保留 v2，不 migrate** |
| **好处** | 万一 2.3 出问题，回滚 1.7.22 时 **config 无需回退**，回滚更干净 |

**唯一例外**：如果实施中发现必须用 containerd 2.x 特有字段，才考虑迁移到 v3（2.x 最低要求 v3）。届时：
```bash
cp /etc/containerd/config.toml /etc/containerd/config.toml.v2.bak
containerd config migrate > /tmp/config.new.toml
# 审查 diff，确认无误后再替换
diff /etc/containerd/config.toml /tmp/config.new.toml
```
⚠️ **注意**：migrate 到 v4 会让 config **无法被 containerd 1.7 读取** → 破坏回滚能力。**强烈建议最多 migrate 到 v3**（2.0-2.2 用 v3，2.3 也支持 v3）。

### 7.2 升级过程中需要改的 config 项

| 项 | 现状 | 改为 | 原因 |
|---|---|---|---|
| `sandbox_image` | `registry.aliyuncs.com/google_containers/pause:3.9` | containerd 2.3 默认 pause 镜像（决策 5）| 决策 |
| `SystemdCgroup` | `true` | **保持不变** | 与 kubelet 一致，无需动 |
| `version` | 2 | **保持不变** | 2.x 兼容读|
| registry 四个子段 | 空 | **保持不变** | 已查无条目 |
| 其余 | — | **保持不变** | 原则：本次只改必要项 |

### 7.3 回滚方案

**containerd 回滚（单节点）**：
```bash
# 1. 驱逐
kubectl cordon <node>
# 2. 恢复二进制
cp /usr/local/bin/containerd.bak-1.7.22 /usr/local/bin/containerd
cp /usr/local/sbin/runc.bak-1.3.3 /usr/local/sbin/runc   # 或/usr/bin/runc
# 3. 恢复 config（如果改过 sandbox_image）
cp /etc/containerd/config.toml.bak /etc/containerd/config.toml
# 4. 重启
systemctl restart containerd
# 5. 验证
containerd --version   # 应为 1.7.22
crictl ps -a
# 6. 恢复调度
kubectl uncordon <node>
```
**因为保留 config v2，回滚时 config 无需额外处理** —— 这就是不 migrate 的核心收益。

**K8s 回滚**：kubeadm 不支持降级。只能：
- 从备份恢复 etcd + 恢复 kubeadm config（复杂）
- **实际策略：每级升级前对 etcd 做快照**，出问题从快照恢复
- **强烈建议**：每个小版本升级前执行 `etcdctl snapshot save`

## 十二、★ 新增升级线：kube-proxy IPVS → iptables（决策 11）

### 12.1 迁移原因

- **K8s 1.35 弃用 IPVS（KEP-5495），1.38 移除**
- 官方迁移路径：1.35 先在测试环境验证 nftables → 小集群可直接用 iptables
- **本集群 6 节点，雷浩决策用 iptables**（最简单，6 节点规模 iptables 性能完全足够）

### 12.2 迁移前必须确认（★ 关键）

```bash
# 确认当前 ipvs 虚拟服务数量（决定迁移难度）
ssh worker01 'ipvsadm -Ln | wc -l'    # 实测 366 条
```

**366 条 IPVS 规则** —— 这些是 kube-proxy 自动生成的 Service 虚拟服务，**不会自动迁移到 iptables**，需要 kube-proxy 重建 iptables 规则。

**★ 风险点**：
- 迁移瞬间**所有 Service 连接会短暂中断**（新规则生效前的窗口）
- 有状态服务（Kafka、PostgreSQL/CNPG）连接会断，但客户端会重连
- 建议**业务低峰期操作**

### 12.3 迁移步骤

```bash
# 1. 导出当前 kube-proxy 配置
kubectl -n kube-system get cm kube-proxy -o jsonpath='{.data.config\.conf}' > /tmp/kube-proxy.conf
# 编辑：mode: "ipvs" → mode: "iptables"，并清理 ipvs 段配置

# 2. 替换配置
kubectl -n kube-system patch cm kube-proxy --type=merge \
  -p '{"data":{"config.conf":"'"$(cat /tmp/kube-proxy.conf)"'"}}'

# 3. 重启 kube-proxy
kubectl -n kube-system rollout restart ds/kube-proxy
kubectl -n kube-system rollout status ds/kube-proxy --timeout=120s

# 4. 验证
kubectl -n kube-system logs -l k8s-app=kube-proxy --tail=20   # 确认用 iptables
ssh worker01 'iptables -t nat -L KUBE-SERVICES -n | wc -l'        # 应有规则
ssh worker01 'ipvsadm -Ln 2>/dev/null | wc -l'                    # 应为 0

# 5. 业务验证（跨节点 Service 访问）
```

### 12.4 iptables vs nftables 的选择说明

雷浩选了 iptables，这里说明取舍：

| 项 | iptables | nftables |
|---|---|---|
| 规则数上限 | 较严（单链 8192 条默认）| 大得多 |
| 性能 | 6 节点足够 | 更好 |
| K8s 支持 | 全版本支持 | 1.31+ GA |
| 配置复杂度 | 简单 | 需 nftables 后端 |

**6 节点集群 + 366 条规则，iptables 完全够用**。nftables 更现代但引入新变量，不适合升级期间同时变更两个东西。

# 追加：第四阶段 — Calico 安装方式查证（2026-10-02 晚，最后一项）

## 十六、★ Calico 安装方式：**manifest 安装（非 tigera-operator）**

### 16.1 判定依据（三条独立证据）

| 证据 | 实测结果 | 说明 |
|---|---|---|
| 无 tigera-operator Deployment | `kubectl get deploy,ds,pod -A | grep -ci tigera` → **0** | 没有 operator |
| 无 Installation CR | `kubectl get installations.operator.tigera.io` → **resource type 不存在** | operator 的标志性 CRD 未安装 |
| CRD 有 last-applied-configuration | `ippools.crd.projectcalico.org` 的 annotations 含 `kubectl.kubernetes.io/last-applied-configuration` | **典型 `kubectl apply -f manifest.yaml` 特征** |
| 无 operator 管理标签 | `calico-node` DS 的 labels 只有 `{"k8s-app":"calico-node"}` | operator 装的会带 `installationID` 等标签 |

**结论**：当初是**下载 Calico 的 `calico.yaml` manifest，用 `kubectl apply` 装的**。

### 16.2 Calico 资源清单

| 资源 | 名称 | 状态 |
|---|---|---|
| DaemonSet | `calico-node` | 6/6 Ready，259 天 |
| Deployment | `calico-kube-controllers` | 1/1 Ready，259 天 |
| 镜像 | `calico/node:v3.27.4` + `calico/kube-controllers:v3.27.4` | 版本一致 |

### 16.3 ★★ 重要发现：Calico 配置细节（升级必须对齐）

**① 使用 BIRD（BGP）后端**

```yaml
# cm/calico-config
calico_backend: "bird"          # ★ BIRD，不是 felix-only
cni_network_config: { ... }      # cniVersion 0.3.1
veth_mtu: "0"
typha_service_name: "none"       # 未用 Typha
```

`calico-node` 环境变量：
```
DATASTORE_TYPE=kubernetes
CALICO_NETWORKING_BACKEND=bird   （来自 calico-config ConfigMap）
CLUSTER_TYPE=k8s,bgp★            # ★ BGP 模式
IP=autodetect
CALICO_IPV4POOL_IPIP=Always      # IPIP Always
CALICO_IPV4POOL_VXLAN=Never
FELIX_IPINIPMTU=来自 calico-config
```

**IPPool 配置**：
```
name: default-ipv4-ippool
cidr: 10.244.0.0/16
ipipMode: Always          # ★ IPIP Always（封装模式）
vxlanMode: Never
natOutgoing: True
nodeSelector: all()
```

**② ★★ FelixConfiguration 有两项非默认 BPF 配置（升级风险点）**

```yaml
# FelixConfiguration/default
bpfConnectTimeLoadBalancing: "TCP"                # ★ 非默认（默认是 Disabled）
bpfHostNetworkedNATWithoutCTLB: "Enabled"         # ★ 非默认
floatingIPs: "Disabled"
logSeverityScreen: "Info"
reportingInterval: "0s"
```

**这两项是集群里实际生效的 BPF 配置**，而 **Calico v3.32 对 BPF 默认值和字段有调整**。升级时若不对齐，BPF 行为可能变化。

### 16.4 自定义 CRD 实例（很少，迁移负担低）

| CRD | 实例数 | 影响 |
|---|---|---|
| IPPool | 1 | `default-ipv4-ippool`，升级时保留即可 |
| BGPPeer | **0** | 无自定义 BGP peer |
| BGPConfiguration | **0** | 无自定义 BGP 配置 |
| BGPFilter | **0** | 无 |
| GlobalNetworkPolicy | **0** | 无全局网络策略 |
| NetworkPolicy | **0** | **无任何 NetworkPolicy**（跨节点访问不受策略限制）|

**结论**：Calico 自定义配置极少，**只有 1 个 IPPool + 1 个 FelixConfiguration**，迁移负担低。

## 十七、Calico manifest 升级路径（★ 因安装方式而定）

### 17.1 manifest 安装的升级步骤

```bash
# 1. 备份当前manifest 和 CRD
kubectl get crd -o yaml > calico-crds-backup.yaml
kubectl get ds calico-node -n kube-system -o yaml > calico-node-backup.yaml
kubectl get deploy calico-kube-controllers -n kube-system -o yaml > calico-kc-backup.yaml
kubectl get cm calico-config -n kube-system -o yaml > calico-config-backup.yaml
kubectl get ippool default-ipv4-ippool -o yaml > calico-ippool-backup.yaml
kubectl get felixconfiguration default -o yaml > calico-felix-backup.yaml

# 2. 下载目标版本 manifest
curl -o calico-v3.32.yaml https://raw.githubusercontent.com/projectcalico/calico/v3.32.2/manifests/calico.yaml

# 3. ⚠️ 关键：应用新版 CRD（先CRD，后 workload）
kubectl apply -f calico-v3.32.yaml

# 4. 验证 Calico 恢复
kubectl -n kube-system get pods -l k8s-app=calico-node
kubectl get nodes       # 应全部 Ready
```

### 17.2 ★ 升级时必须对齐的配置（否则行为会变）

| 配置 | 当前值 | 升级动作 |
|---|---|---|
| `calico_backend` | `bird` | 新manifest 默认可能是 `felix`，**必须改回 bird** |
| `CLUSTER_TYPE` | `k8s,bgp` | 保留 |
| IPPool ipipMode | `Always` | 保留（若变Never，跨节点 Pod 网络会断）|
| IPPool cidr | `10.244.0.0/16` | 保留 |
| `bpfConnectTimeLoadBalancing` | `TCP` | ⚠️ 确认 v3.32 是否仍支持此字段 |
| `bpfHostNetworkedNATWithoutCTLB` | `Enabled` | ⚠️ 确认 v3.32 是否仍支持 |
| veth_mtu | `0` | 保留 |

### 17.3 ★ 升级前必做的三项确认

| # | 确认项 | 方法 |
|---|---|---|
| 1 | **v3.32 manifest 是否需改 IPIP 模式** | 新 manifest 默认 IPPool 可能是 Never，需改回 Always |
| 2 | **BPF 字段是否仍支持** | v3.32 release notes 查 `bpfConnectTimeLoadBalancing` / `bpfHostNetworkedNATWithoutCTLB` |
| 3 | **是否先升到 v3.30/3.31 过渡** | 跨 5 个 minor 直升 v3.32 风险较高，**建议考虑分 2 步升** |
