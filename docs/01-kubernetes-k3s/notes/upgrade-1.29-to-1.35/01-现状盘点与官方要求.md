### 1.3 containerd 安装方式（★ 升级方案的关键差异点）

| 项 | 6 节点实测结果 | 对升级的影响 |
|---|---|---|
| 二进制路径 | `/usr/local/bin/containerd` | **手动安装，非 RPM/DEB 包** |
| systemd unit ExecStart | `/usr/local/bin/containerd` | 无 `containerd.io` 包依赖，替换二进制即可 |
| RPM 包 containerd | **未安装** | `dnf update containerd` **无效** |
| containerd.io 包 | **未安装** | 官方 deb/rpm 升级路径**不适用** |
| runc 路径 | m01=`/usr/bin/runc`；其余=`/usr/local/sbin/runc` | ★ **节点间不一致**，需分别处理 |

**结论**：这套 containerd 是**手动二进制安装**（很可能是二进制直接解压到 `/usr/local/bin`）。升级方式不能沿用 `yum install containerd.io` 的官方教程，必须走「备份二进制 → 下载新版 → 替换 → 重启 systemd 服务」的手工路径，或改用官方 `containerd.io` 包重建（后者会改变安装形态，需评估）。

## 二、官方要求核实（2026-10-02 完成，附链接）

### 2.1 containerd 官方 Kubernetes 版本矩阵

来源：https://containerd.io/releases/#kubernetes-support

| K8s 版本 | 官方推荐 containerd 版本 | CRI |
|---|---|---|
| 1.29 | （1.7.x 系列）| v1 |
| 1.32 | 2.1.0+, 2.0.1+, 1.7.24+, 1.6.36+ | v1 |
| 1.33 | 2.1.0+, 2.0.4+, 1.7.24+, 1.6.36+ | v1 |
| 1.34 | 2.1.3+, 2.0.6+, 1.7.28+, 1.6.39+ | v1 |
| **1.35** | **2.2.0+, 2.1.5+, 1.7.28+** | v1 |
| 1.36 | 2.3.0+, 2.2.0+ | v1 |
| 1.37 | 2.4.0+, 2.3.0+ | v1 |

**对本集群的含义**：
- 当前 **1.7.22** 支持 K8s 到 **1.33**（1.34 就需要 1.7.28+ 了）
- 要升到 **1.35**，containerd 至少需 **1.7.28**（或 2.x）
- 官方推荐用于 1.35 的是 **2.2.0+ / 2.1.5+ / 1.7.28+**

### 2.2 K8s 1.35 关于 containerd 1.x 的弃用（关键）

来源：
- https://kubernetes.io/blog/2025/11/26/kubernetes-v1-35-sneak-peek/ （Sneak Peek）
- https://kubernetes.io/blog/2025/12/17/kubernetes-v1-35-release/ （正式发布）

官方原文要点：
> "This is a final warning that if you are using containerd 1.X, you must switch to 2.0 or later before upgrading Kubernetes to the next version."
>
> "**Final call for containerd v1.X** — This serves as an important reminder: before upgrading to the next Kubernetes version, you must switch to containerd 2.0 or later."

**★ 关键结论**：**K8s 1.35 是最后一个支持 containerd 1.x 的版本；到 1.36 时 containerd 1.x 将被移除。** 注意时间点：官方要求的是**升到「下一个版本」（即 1.36）之前切到 containerd 2.0+**，不是「升 1.35 之前」。1.35 本身仍支持 containerd 1.7.28+（见 §2.1 矩阵）。
本方案仍先升 containerd，理由是**现役 1.7.22 低于 1.35 的矩阵下限 1.7.28，且 1.7 分支 2026-09 已 EOL**——不是「1.35 要求 2.0」。

### 2.3 containerd 2.x 版本状态与 EOL

来源：https://containerd.io/releases/

| containerd 分支 | 状态 | 起始 | EOL |
|---|---|---|---|
| 1.6 | End of Life | 2022-02-15 | 2025-08-23 |
| **1.7** | **LTS** | 2023-03-10 | **2026-09** |
| **2.0** | **LTS** | 2024-11-05 | **2027-03** |
| 2.1 | End of Life | 2025-05-07 | 2026-07-03 |
| **2.2** | **Active** | 2025-11-05 | **2026-11-06** |
| **2.3** | **LTS** | 2026-04-30 | **2028-04-30** |
| 2.4 | RC | 2026-09-15 | 2027-05-15 |

★ **重要时效提醒**：**containerd 1.7 LTS 已于 2026-09 EOL**，当前已无官方安全补丁。这也强化了「尽快升到 2.x」的紧迫性——现在 containerd 1.7.22 不仅版本低于 1.35 要求，且其所在分支已停止维护。

**候选目标版本分析**：

| 候选 | 状态 | 优势 | 劣势 |
|---|---|---|---|
| 2.2.x | Active，EOL 2026-11 | 官方推荐用于 K8s 1.35；Active 支持期 | 仅剩约1 个月支持（2026-11 EOL），非LTS |
| 2.3.x | **LTS**，EOL 2028-04 | 最长支持期（到 2028）；config v4；官方支持 1.7(LTS)→2.3(LTS) 直连升级 | 相对新（2026-04 发布），K8s 1.35 矩阵里未列 2.3（但 1.36 才推荐 2.3）；比 2.2 激进 |
| 2.0.x | LTS，EOL 2027-03 | LTS；官方为 1.35 兼容的最低 2.x | 2.1/2.2 特性缺失；EOL 比 2.3 早 |

★ **倾向 2.3.x（LTS）**，理由：支持期最长（2028-04）、是当前最新 LTS、官方明确支持「1.7(LTS) → 2.3(LTS)」直接升级路径。但**「需人工确认」**：K8s 1.35 官方推荐矩阵列的是 2.2.0+/2.1.5+/1.7.28+，未直接列 2.3（2.3 是 1.36 的推荐）。若求稳，可选 2.2.x（Active，1.35 官方推荐）但支持期短。这个取舍需雷浩决定——**偏稳（2.2.x，官方 1.35 推荐，但 2026-11 EOL）vs 偏长周期（2.3.x LTS，2028-04 EOL，但 1.35 矩阵未列）**。

### 2.4 containerd 升级路径规则（官方）

来源：https://containerd.io/releases/#upgrade-path

官方规则：
> "Upgrades are supported for sequential minor releases. For example, an upgrade from 2.0 to 2.1 is supported, but an upgrade from 2.0 to 2.2 is not. Patch releases are always backward compatible with their minor version."
>
> "In addition to sequential minor release upgrades, direct upgrades between sequential LTS releases are also supported. For example, a direct upgrade from 1.7 (LTS) to 2.3 (LTS) will be tested and supported, but 1.7 (LTS) to 2.6 (LTS, tentatively) will not."
>
> "There are no compatibility guarantees with upgrades to *major* versions. For 2.0, migration was added to ensure upgrading from 1.6 or 1.7 to 2.0 is easy."

**解读（本集群适用）**：
- **1.7 → 2.x 是跨 major 升级，官方无兼容保证**（虽然 2.0 专门做了从 1.6/1.7 的迁移支持）
- 但「1.7(LTS) → 2.3(LTS)」这条**跨 major 的 LTS 直连路径是官方测试并支持的**
- 1.7 → 2.0 有专门的迁移支持（1.6/1.7 最新版会在 config 不兼容 2.0 时给出 deprecation warning）
- 官方建议：**若 1.7 升级时出现 deprecation warning，说明 config 与 2.0 不兼容，需先在 1.7 上迁移 config**

### 2.5 config.toml 版本与迁移（★ 官方已更新到 v4）

来源：https://containerd.io/releases/#daemon-configuration

官方原文：
> "The daemon's configuration file... is versioned and backwards compatible. The `version` field... If no version number is specified then it is assumed to be version 1. **The latest version is `version = 4`.** The configuration is automatically migrated to the latest version on each startup, leaving the configuration file unchanged. To avoid the migration and optimize the daemon startup time, use **`containerd config migrate`** to output the configuration as the latest version. All prior versions are supported by migration."
>
> "**Migrating a configuration to the latest version will limit the prior versions of containerd in which the configuration can be used.** It is suggested not to migrate your configuration file until you are confident you do not need to quickly rollback your containerd version."

**config 版本 ↔ 最低 containerd 版本对应表（官方）**：

| Config Version | 最低 containerd 版本 |
|---|---|
| 1 | v1.0.0 |
| 2 | v1.3.0 |
| 3 | v2.0.0 |
| 4 | v2.3.0 |

★ **本集群 config.toml 当前是 version 2**：
- containerd 2.x 最低要 config v3（2.0/2.1/2.2 用 v3）
- 若升到 containerd 2.3 LTS，其配置可用 v4
- 官方强调：**迁移到最新 config 会限制「可回退的旧 containerd 版本」**（因为旧 containerd 读不了高版本 config）
- 容器启动时会自动迁移内存中的配置，但**不改动磁盘上的文件**；`containerd config migrate` 是显式输出为最新版

**★ 迁移注意事项（回滚约束）**：
- config v2 现状下，containerd 2.x 会自动按 v3 解析——**不主动 migrate 到 v4，保留 v2 文件，反而更利于回滚到 1.7**
- 建议：**升级时保留现有 config.toml v2 不动**（containerd 2.x 向下兼容读 v2），除非有必须用新字段；这样万一 containerd 2.x 出问题，回滚 1.7 时 config 无需回退
- 若确需 migrate，务必先备份，且 migrate 后不要急于删除 1.7 二进制（回滚时需要 config 回到 v2）

### 2.6 containerd 2.x 弃用/移除的关键配置（会影响本集群的部分）

来源：https://containerd.io/releases/ （Deprecated 表格，节选相关项）

官方从 v2.0 起弃用/移除的配置（节选与本集群相关）：

| 旧配置 | 弃用版本 | 移除版本 | 替代方案 |
|---|---|---|---|
| `[plugins."io.containerd.grpc.v1.cri".registry].mirrors` | v1.5 | v2.7 | 用 `config_path` |
| `[plugins."io.containerd.grpc.v1.cri".registry].configs` | v1.5 | v2.7 | 用 `config_path` |
| `[plugins."io.containerd.grpc.v1.cri".registry].auths` | v1.3 | v2.7 | 用 `ImagePullSecrets` |
| `[plugins."io.containerd.cri.v1.runtime".enable_cdi` | v2.2 | v2.4 | CDI 始终启用 |

★ **对本集群**：

## 三、各节点 containerd 是否需要升级（结论）

| 节点 | 当前 | 目标需求（K8s 1.35）| 是否需升级 | 理由 |
|---|---|---|---|---|
| m01 | 1.7.22 | 1.7.28+ 或 2.x | **需要** | 1.7.22 < 1.7.28；且 1.7 分支已 EOL（2026-09）；且官方要求 1.35 前必须切 2.0+ |
| master01 | 1.7.22 | 同上 | **需要** | 同 m01 |
| master02 | 1.7.22 | 同上 | **需要** | 同 m01 |
| worker01 | 1.7.22 | 同上 | **需要** | 同 m01 |
| worker02 | 1.7.22 | 同上 | **需要** | 同 m01 |
| worker03 | 1.7.22 | 同上 | **需要** | 同 m01 |

**结论：6 个节点全部需要升级 containerd。** 且由于版本完全一致，可按同一流程批量处理（仍建议逐节点滚动，不并行）。

### 3.1 推荐的 containerd 目标版本（★ 需雷浩确认）

**首选：containerd 2.3.x（LTS）**
- 支持期到 2028-04（最长）
- 官方支持「1.7(LTS)→2.3(LTS)」直接升级
- 但 K8s 1.35 官方推荐矩阵列的是 2.2.0+/2.1.5+/1.7.28+，未直接列 2.3

**备选：containerd 2.2.x（Active）**
- K8s 1.35 官方推荐
- 但 2026-11-06 EOL（支持期很短）

**★ 待人工确认的取舍点**：
1. 选 2.3.x（LTS 长周期，但非 1.35 官方矩阵推荐）还是 2.2.x（1.35 官方推荐，但 2026-11 EOL）？
2. 若选 2.3.x，config 是否要 migrate 到 v4？（建议不 migrate，保留 v2 以便回滚）

## 五、升级顺序总纲（初稿，详细滚动策略待下一步细化）

### 5.1 大方向（遵循官方指引 +你的要求）

```
阶段 A：升级 containerd（K8s 仍为 1.29）
  目标：1.7.22 → 2.x（先在 1 台上验证，再滚动其余）
  验证：crictl / 容器不重建 / 节点 Ready
  理由：官方明确「升 K8s 到 1.35 前必须先切 containerd 2.0+」

阶段 B：逐级升级 K8s（containerd 已就位）
  1.29 → 1.30 → 1.31 → 1.32 → 1.33 → 1.34 → 1.35
  规则：不能跨小版本，每级验证后再进下一级
```

### 5.2 节点滚动策略（原则，详细命令待下一阶段）

- **逐节点**（不并行），worker 先于 control-plane 还是相反需评估
- 每节点：`cordon` → `drain` → 升级 → 验证 → `uncordon`
- ★ **control-plane 节点特殊性**：本集群 control-plane 是静态 Pod，drain 需注意 etcd/apiserver 的处理（需人工确认 drain 行为）

## ⚠️ 数据修正记录（2026-10-02 执行前复核发现）

### runc 版本：阶段一盘点有误

**阶段一文档记载**：`runc 1.3.3（6 节点一致）`

**实测复核结果**：

| 节点 | containerd | runc | runc 路径 |
|---|---|---|---|
| m01 | 1.7.22 | **1.3.3** | /usr/bin/runc |
| master01 | 1.7.22 | **1.1.14** | /usr/local/sbin/runc |
| master02 | 1.7.22 | **1.1.14** | /usr/local/sbin/runc |
| worker01 | 1.7.22 | **1.1.14** | /usr/local/sbin/runc |
| worker02 | 1.7.22 | **1.1.14** | /usr/local/sbin/runc |
| worker03 | 1.7.22 | **1.1.14** | /usr/local/sbin/runc |

**错误原因**：阶段一盘点时我 SSH 到 m01（唯一免密可连的节点）读取了 containerd/runc 版本，然后**推断为6 节点一致**，未逐台验证。

**这正是我已在记忆中记录的教训**：「验证时不能只看样本或推测，需逐实例实测」——同类错误第 5 次。

**对升级方案的影响**：
- ❌ 不改变目标：runc 仍需升级到 1.4.3（containerd 2.3.2 官方内置版本）
- ✅ **强化了升级 runc 的必要性**：5 台节点还在 1.1.14，比 1.3.3 更旧
- ✅ **runc 路径不一致的处置（脚本已内置）仍然必要**：m01=/usr/bin，其余=/usr/local/sbin

**教训重申**：盘点阶段「ssh 单节点 + 推断全部」的做法必须改为「逐台实测」。已在脚本中改为逐台读取，避免重犯。
