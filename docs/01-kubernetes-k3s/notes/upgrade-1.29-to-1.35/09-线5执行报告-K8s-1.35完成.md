## 三、镜像加速配置（重要遗留配置）

本环境无法直接访问 `registry.k8s.io` 和 Docker Hub。已配置 **1ms.run** 作为 containerd 全局 mirror。

### 1ms.run 用法

1ms.run **不是路径代理**（`1ms.run/library/busybox` 返回 404），而是**按仓库分子域名**：

| 子域名 | 对应仓库 |
|---|---|
| `k8s.1ms.run` | registry.k8s.io |
| `docker.1ms.run` | docker.io |
| `quay.1ms.run` | quay.io |
| `ghcr.1ms.run` | ghcr.io |

### 配置文件位置

6 节点均已配置：

```
/etc/containerd/certs.d/registry.k8s.io/hosts.toml
```

```toml
server = "https://registry.k8s.io"

[host."https://k8s.1ms.run"]
  capabilities = ["pull", "resolve"]
```

containerd 2.x 通过 `config_path = "/etc/containerd/certs.d"` 自动加载该目录下的 `hosts.toml`。

**验证方式**：删除本地镜像后用原名 `registry.k8s.io/...` 拉取成功——说明所有 Pod 镜像地址无需修改，K8s 自动走加速。

### 关于 DaoCloud

`docker.m.daocloud.io` **只能代理 Docker Hub**，无法代理 `registry.k8s.io`（返回 `HEAD request failed`），不适用于本场景。

## 四、执行过程中发现并修复的问题

### 问题 1：kubeadm 版本必须先于 apply（CP 节点）

**现象**：
```
error execution phase preflight: the version argument is invalid
- Specified version to upgrade to "v1.33.13" is at least one minor release
  higher than the kubeadm minor release (33 > 32)
```

**根因**：CP 节点的执行顺序错了。kubeadm 二进制必须先升级到目标版本，`kubeadm upgrade apply` 才能通过版本检查。

**修复后正确顺序**：
```
安装包（kubeadm/kubelet/kubectl） → kubeadm upgrade apply → 重启 kubelet
```

**注意**：不能提前重启 kubelet —— 会导致静态 Pod 用旧 manifest 重建，触发健康检查超时。

---

### 问题 2：kubeadm 1.33 成功提示语变更

**现象**：apply 实际成功（耗时 7.9s，输出 `[upgrade] SUCCESS!`），但脚本报"apply 失败"。

**根因**：脚本用 `grep -q "upgrade/successful"` 判断，而 kubeadm 1.33 改用了新文案：
- ≤ 1.32：`[upgrade/successful] SUCCESS!`
- ≥ 1.33：`[upgrade] SUCCESS! A control plane node...`

**修复**：改为兼容多版本
```bash
grep -qE "upgrade/successful|SUCCESS!|successfully upgraded"
```

---

### 问题 3：kube-state-metrics 镜像内容损坏（全节点）

**现象**：镜像显示 19.3MB，但导出仅 725K，缺 content blob：
```
ctr: failed to get reader: content digest sha256:fab8c4b3...: not found
```

**根因**：镜像**从未被正确拉取完整**。此前未暴露是因为容器已在运行，containerd 不再校验内容。执行 `crictl rm -a` 后重建 Pod 才暴露。

**修复**：经 1ms.run 拉取完整镜像（导出 28MB），并把 KSM Deployment 镜像地址改为 `k8s.1ms.run/kube-state-metrics/kube-state-metrics:v2.18.0`。

**结果**：Prometheus targets 从 114 恢复到 125/125。

---

### 问题 4：registry.k8s.io 间歇性 insufficient_scope

**现象**：worker01 拉取 registry.k8s.io 镜像间歇性返回 `pull access denied ... insufficient_scope`，多次重试失败；但其他节点同时正常。

**结论**：不是节点问题，是上游 registry 的间歇性故障。

**修复**：配置 1ms.run 全局 mirror（见第三节），彻底解决。

---

### 问题 5：脚本验证逻辑误报（3次）

| 级别 | 误报内容 | 真实状态 |
|---|---|---|
| 1.33 | DNS 异常、targets 掉过多 | DNS 正常，targets 后续恢复 125/125 |
| 1.34 | Kafka 异常、DNS 异常 | Kafka Ready=True，DNS 正常 |
| 1.35 | DNS 异常 | DNS 正常解析 10.96.0.1 |

**根因**：
- Kafka：jsonpath 写在 `$(...)` 内被吞，改用 `--no-headers | awk`
- DNS：`grep -c` 在 `$(...)` 中返回空值，改为直接判断是否含目标 IP
- targets：验证时机在 Pod 重启后 60s，采集未恢复完成

**教训**：验证脚本本身需要验证。连续 3 次误报后，改为**升级后独立实测**再判断，不依赖脚本的 FAIL 标记。

---

### 问题 6：crictl rm -a 的副作用（加固引入）

我在 `cleanup_pods` 中加入的清理步骤，会连带清除节点本地镜像缓存。在镜像不可重新拉取的环境中，这会导致节点失去离线恢复能力。

**处置**：
- 后续级别已移除该步骤
- 通过全局 mirror 解决镜像拉取问题
- 记录为教训：**清理容器前需确认镜像可重建**

## 附录 A：n8n 镜像 ImagePullBackOff 解决

### 现象

`n8n/n8n-7c8ddcbd96-pszmr` 长期 ImagePullBackOff。镜像 `docker.n8n.io/n8nio/n8n:2.14.2` 实际解析到 `registry-1.docker.io`，本环境无法访问：

```
dial tcp 208.101.21.43:443: i/o timeout
```

### 关键点：SWR 仓库路径

华为云 SWR 托管镜像时，路径保留**原始 registry 域名**作为目录名。n8n 的正确路径是：

```
swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.n8n.io/n8nio/n8n:2.14.2
                                    ^^^^^^^^^^^^^^ 原始 registry，不是 docker.io
```

我最初探测的 `ddn-k8s/ghcr.io/n8n-io/n8n:2.7.0` 是**另一个镜像**（ghcr.io 上的旧版 2.7.0），不是本集群在用的 2.14.2。

### 解决步骤

1. 验证 SWR 匿名拉取可用（无需凭据）
   ```
   crictl pull swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.n8n.io/n8nio/n8n:2.14.2
   → Image is up to date for sha256:22511cc8b434a9ce... (289MB)
   ```

2. 备份 Deployment
   ```bash
   kubectl -n n8n get deploy n8n -o yaml > n8n-deploy-backup.yaml
   ```

3. patch 镜像地址
   ```bash
   kubectl -n n8n patch deployment n8n --type=json \
     -p '[{"op":"replace","path":"/spec/template/spec/containers/0/image",
          "value":"swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.n8n.io/n8nio/n8n:2.14.2"}]'
   ```

4. 删除卡住的 Pod 触发重建

### 结果

```
n8n-7f659c7655-blr5k   1/1 Running
cloudflared-6fd6494789-96hzm   1/1 Running
PVC n8n-pvc            Bound 5Gi（未改动）
版本: 2.14.2（与原版本一致，无降级）
工作流 "My workflow" 已激活
Editor: https://n8ntrace.ccwu.cc
```

### 经验

华为云 SWR 的 `ddn-k8s` 这类命名空间，路径规则是 `<SWR域名>/<命名空间>/<原始registry域名>/<仓库路径>:<tag>`。需要与提供者确认原始 registry 域名，不能凭猜测替换。

当前容器日志显示 `Found unfinished executions: 631` 和 `Marked executions as crashed` — 这是长期停机导致的，属预期行为，不影响工作流数据完整性。
