## 1. 根因复盘（速览）

### 1.1 Tempo3PodCrashLooping（4 个 Pod）
- **window A**（10-05 22:31~22:41 +0800）：集群 ~37 个工作负载批量重建，Strimzi Kafka 同批重建但更晚就绪 → `tempo3-block-builder-0 / live-store-0 / metrics-generator` 启动时连不上 Kafka，重试 10 次后显式退出（日志 `kafka broker not ready after 10 retries`），每个崩 4~5 次后随 Kafka 就绪自愈。
- **window B**（10-06 15:43~15:51 +0800）：`tempo3-query-frontend` 遭遇 DNS i/o timeout（解析 `_memcached-client._tcp`）+ `0 queriers connected` → `/ready` 长期不过 → **liveness（也指向 /ready）** 逐次杀死，8 次后自愈。

### 1.2 KubePodHighRestartCount（argocd-repo-server，12 次）
- 全部 12 次发生在 window B（10-06 15:31~16:01 +0800，含 strimzi-cluster-operator×6、query-frontend×8 同窗口）。
- **第一轮判断**：Kube-proxy DaemonSet 滚动导致 Service/DNS/API 流量瞬时抖动 → 各组件本地 HTTP 探针超时失败被反复杀死：`/metrics/healthz?full=true` 探针 chart 默认 `timeoutSeconds=1、period 10s、failureThreshold=3`（任何 30~40s 阻塞即被杀），且无 requests（BestEffort）。日志：`got signal terminated → clean shutdown`（退出 0）。
- **第二轮修正（§8.4，重要）**：上述"抖动后自愈"判断不完整。实测 ArgoCD v3.2.4 的 metrics 监听 **根本不提供 `/metrics/healthz?full=true` 这个路由（无条件 404）**，而第一轮只调了探针时序、路径未动 → pod 在修复后**仍在持续被杀**（新 pod 40 分钟内重启 11 次）。**真根因是探针路径与 ArgoCD v3.2.4 不兼容（旧 chart 渲染的 v2 时代路径），形成持续 404 误杀循环**；window B 的网络抖动只是同期放大器。终修：liveness 路径改为 `/healthz`（见 §8.4）。

## 4. 处置③：tempo3-query-frontend 探针修正

问题在于 liveness 与 readiness **都指向 `/ready`**：一旦"未就绪但进程健康"（如 querier 暂时断开），就会被 liveness 当成"死亡"反复杀死。改为 liveness 只做进程级存活检查（`/metrics`），`/ready` 专用于流量摘除。

**修改前：**
```yaml
livenessProbe:
  httpGet: {path: /ready, port: http-metrics}      # 未就绪 == 被杀
readinessProbe:
  httpGet: {path: /ready, port: http-metrics}
```

**修改后：**
```yaml
livenessProbe:
  httpGet: {path: /metrics, port: http-metrics, scheme: HTTP}
  initialDelaySeconds: 60
  periodSeconds: 30
  timeoutSeconds: 3
  failureThreshold: 6
readinessProbe:
  httpGet: {path: /ready, port: http-metrics}
  initialDelaySeconds: 30
  periodSeconds: 10
  timeoutSeconds: 1
```

**执行命令：**
```bash
kubectl patch deployment tempo3-query-frontend -n logging --type=strategic -p '{
  "spec":{"template":{"spec":{"containers":[{"name":"query-frontend",
    "livenessProbe":{"httpGet":{"path":"/metrics","port":"http-metrics","scheme":"HTTP"},"initialDelaySeconds":60,"periodSeconds":30,"timeoutSeconds":3,"failureThreshold":6,"successThreshold":1}}]}}}}
'
```

## 8. 第二轮处置（遗留项）：2026-10-07 08:45~09:40 (+0800)

> 背景：第一轮收尾时仍有 `TargetDown(kube-proxy)`、`LokiIngestStalled` 两条历史告警 FIRING；随后操作中又暴露 tempo 组件 liveness 隐患、repo-server 重启未根治、以及若干窗口化规则"计数器断链"误报尾巴。本轮回环闭环，最终 `/api/v1/alerts` 仅剩 `Watchdog`。

### 8.1 kube-proxy 指标抓不到（TargetDown 根因 & 修复）

**现象**：`up{job="kube-proxy"}` 自 10-06 06:32Z 起全 0，其余组件正常。

**排查**：
1. ConfigMap `kube-proxy` 中 `metricsBindAddress: 0.0.0.1:10249` —— **拼写错误**（0.0.0.1 不是 0.0.0.0）；
2. 但 DaemonSet 容器 command **没有 `--config`**，ConfigMap 的该值实际上不被读取。kube-proxy v1.35.9 未显式指定时 **默认把 metrics 绑到 127.0.0.1:10249**，节点 IP:10249 自然拒连。升级（换新镜像）即触发（window B 同期）。

**修复**：
```bash
# ① 更正 ConfigMap（次要修复：kube-proxy Pod 未用 --config，该值在运行态并不生效；保留此项避免后续误判为根因）
kubectl get cm kube-proxy -n kube-system -o json | python3 -c '
import sys,json
d=json.load(sys.stdin)
d["data"]["config.conf"]=d["data"]["config.conf"].replace(
  "metricsBindAddress: 0.0.0.1:10249","metricsBindAddress: 0.0.0.0:10249")
json.dump(d,sys.stdout)' | kubectl apply -f -

# ② 根治：command 显式追加 --metrics-bind-address=0.0.0.0（仅影响 metrics 监听，不动转发）
kubectl patch daemonset kube-proxy -n kube-system --type=strategic -p '{
  "spec":{"template":{"spec":{"containers":[{"name":"kube-proxy",
    "command":["/usr/local/bin/kube-proxy","--proxy-mode=iptables",
               "--hostname-override=$(NODE_NAME)",
               "--kubeconfig=/var/lib/kube-proxy/kubeconfig.conf",
               "--metrics-bind-address=0.0.0.0"]}]}}}}
'
kubectl rollout status ds/kube-proxy -n kube-system --timeout=300s
```
> 注意：`--type=merge` 会把 containers[0] 整对象覆盖而丢掉 image，**必须用 `--type=strategic`**。

**验证**：`up{job="kube-proxy"}` → 6 台全 `1`；TargetDown 告警消除。

### 8.2 LokiIngestStalled 规则 job 名不匹配（历史误报根治）

**现象**：自 10-05 14:31Z 起长期 FIRING（早于本次事件，第一轮定为"另一话题"，实操中顺带定位根因）。

**根因**：规则 expr 匹配 `job=~"loki-write|loki-backend|loki-read"`，但实际 `up` 的 job 标签是 **`logging/loki-write` 等（带命名空间前缀，ServiceMonitor 默认 job=<ns>/<名称>）**，正则匹配不到任何序列 → `absent()` 恒真 → 永久告警。**规则写错，非 Loki 故障**。

**修复**（`monitoring/coverage-gap-alerts` 组 `logging-pipeline.rules` rule#2）：

### 8.4 argocd-repo-server 重启循环真根因 & 终修

**现象**：第一轮把探针时序调宽松后，新 pod 仍出现**持续重启**（40 分钟内 11 次，每次存活 ~3 分钟 = 按 period30/failure6 处决）。事件：`Unhealthy Liveness probe failed: HTTP probe failed with statuscode: 404`。

**实证**（直接对 Pod IP:8084 探测）：
```text
GET /metrics/healthz?full=true  → 404 page not found   ← 旧 chart 渲染的 v2 时代路径，v3.2.4 无此路由（无条件 404）
GET /metrics/healthz            → 404 page not found
GET /healthz                    → 200 ok                ← 稳定，process 存活语义
GET /healthz?full=true          → 200 ok (健康时)         ← chart 9.3.2 当前默认（深检查）
```
**结论**：运行中的 Deployment 用的 liveness 路径 `/metrics/healthz?full=true` 在 ArgoCD v3.2.4 上**无条件 404**，kubelet 把它当失败反复杀。第一轮"调时序"只是放缓处决节奏，路径不变仍必死。**这是 repo-server 全部重启的根本原因**（含 window B 的 12 次，网络抖动只是同期放大器）。

**终修**（liveness 改为轻量 `/healthz`，只判进程存活）：
```bash
kubectl patch deployment argocd-repo-server -n argocd --type=strategic -p '{
  "spec":{"template":{"spec":{"containers":[{"name":"repo-server",
    "livenessProbe":{"httpGet":{"path":"/healthz","port":"metrics","scheme":"HTTP"},
     "initialDelaySeconds":15,"periodSeconds":30,"timeoutSeconds":3,
     "failureThreshold":6,"successThreshold":1}}]}}}}
'
kubectl rollout status deployment/argocd-repo-server -n argocd --timeout=180s
```
**验证**：新 pod `argocd-repo-server-85d589b546-c47js` 运行 15+ 分钟 restarts=0、Ready=true，重启循环终止。

### 8.5 窗口化规则"计数器断链"尾巴统一收窄

**现象**：pod 被替换时，`restarts_total` 计数器序列会断裂（旧序列停在 N，新序列从 0），`increase` 在窗口内会算出 ~N 的虚高值 → 窗口化规则仍会长达一个窗口期误报（原 6h 窗口 → 残留 6 小时）。

**统一收窄**（对齐 kube-prometheus 崩溃循环语义）：
```bash
# KubePodHighRestartCount：6h/>10 → 15m/>5（for 10m）
kubectl patch prometheusrule cluster-wide-alerts -n monitoring --type=json -p '[
 {"op":"replace","path":"/spec/groups/3/rules/0/expr","value":"max by (namespace, pod, container) (increase(kube_pod_container_status_restarts_total[15m])) > 5"},
 {"op":"replace","path":"/spec/groups/3/rules/0/for","value":"10m"}
]'
# ArgoCDHighRestart（coverage-gap）：1h/>3 → 15m/>3
kubectl patch prometheusrule coverage-gap-alerts -n monitoring --type=json -p '[
 {"op":"test","path":"/spec/groups/3/rules/1/alert","value":"ArgoCDHighRestart"},
 {"op":"replace","path":"/spec/groups/3/rules/1/expr","value":"sum by (pod) (increase(kube_pod_container_status_restarts_total{namespace=\"argocd\"}[15m])) > 3"}
]'
```
**效果**：任何 deployment/sts 替换造成的虚高残留，最长误报 15 分钟（替换旧序列滑出窗口）即自然归零；真实崩溃循环（单位时间窗口内的突发重启）仍能命中。
